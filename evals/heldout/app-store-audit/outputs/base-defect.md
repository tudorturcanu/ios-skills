# ReceiptBox 1.4.0 (57) - submission readiness review

## Verdict
Not ready as-is. The ITMS-91053 email is explained by a real gap: `PrivacyInfo.xcprivacy` declares only the UserDefaults required-reason API, but the code also uses file timestamp APIs, which need their own declaration. There is also a larger functional problem (empty PDFs) that could cause a rejection under Guideline 2.1.

## Findings

### 1. [Blocker, causes ITMS-91053] Missing NSPrivacyAccessedAPICategoryFileTimestamp declaration
- `PrivacyInfo.xcprivacy:11-21` lists exactly one accessed-API category: `NSPrivacyAccessedAPICategoryUserDefaults` with reason `CA92.1`.
- `Sources/ReceiptStore.swift:26` requests `.contentModificationDateKey` in `contentsOfDirectory(at:includingPropertiesForKeys:)`.
- `Sources/ReceiptStore.swift:32-33` calls `fm.attributesOfItem(atPath:)[.modificationDate]`.
- Both read file modification timestamps. Apple lists these under the "File timestamp APIs" category (`NSPrivacyAccessedAPICategoryFileTimestamp`), and they need a declared reason.
- Fix: add a second dict to `NSPrivacyAccessedAPITypes` with `NSPrivacyAccessedAPICategoryFileTimestamp` and reason `C617.1`. That reason covers timestamps of files inside the app container, which matches the app's own Documents folder (`ReceiptStore.swift:9`). Add `3B52.1` only if the app also reads timestamps of user-granted external files; nothing here does.
- I did not find a call to `.creationDate`, `stat`, `systemUptime`, `volumeAvailableCapacity` or similar, so I see no other missing category in the excerpt. The folder holds only two source files, so other code, which I cannot see, may use more.
- The existing UserDefaults entry is correct. `ReceiptStore.swift:5,13,14` uses `UserDefaults.standard` for app-only data, which matches `CA92.1`.

### 2. [High] Scanner returns empty data, so every saved receipt is a 0-byte "PDF"
- `Sources/ScannerView.swift:25`: `onFinish(Data())  // PDF rendering omitted in this excerpt`.
- If this is the shipped code, `ReceiptStore.save` (`ReceiptStore.swift:17-21`) writes empty files, and the app's core feature does nothing. A reviewer testing the scan flow would likely reject it under 2.1 (App Completeness). Confirm that the real build has the actual PDF rendering. The comment says "excerpt", so I cannot tell from these files alone.
- The `scan` parameter is never used, so the scanned pages are discarded.

### 3. [Medium] Review notes describe a sort setting the code does not use
- `REVIEW_NOTES.txt:4` says "The sort setting is stored locally."
- `ReceiptStore.sortOrder` (`ReceiptStore.swift:12-15`) is stored but never read by `receipts()` (`:24-36`), which always sorts by modification date. No UI for it is visible. Either wire it up or remove it, so the notes and the behavior agree.
- Note that "modification date" is not "scan date". Editing or re-saving a file reorders it.

### 4. [Medium] Unsanitised file name and silent overwrite
- `ReceiptStore.swift:18` builds the path from `name` with no sanitising. A name with `/` or `..` can write outside the intended folder, or fail. There is no collision handling, so `.atomic` silently replaces an existing receipt of the same name. Use a UUID or timestamp name, and strip separators.

### 5. [Low] Timestamp lookup is wasteful and duplicates the resource-key fetch
- `ReceiptStore.swift:26` pre-fetches `.contentModificationDateKey` and then ignores it. The sort comparator (`:31-35`) calls `attributesOfItem` twice per comparison. Read `url.resourceValues(forKeys:)` once per file, then sort. This is an efficiency fix only. It does not change the privacy declaration, which is needed either way.
- `try?` with `?? .distantPast` hides errors.

### 6. [Low] ScannerView delegate is incomplete
- `ScannerView.swift:19-28` only implements `didFinishWith`. There is no `documentCameraViewControllerDidCancel` or `didFailWithError`. Cancel or error then leaves the sheet open, because it relies on the parent's state. Also `c.dismiss` runs after `onFinish`, so a SwiftUI parent that already dismisses the sheet may double-dismiss. Minor, but worth fixing.

### 7. [Low] Info.plist notes
- `Info.plist:6`: `com.example.receiptbox` is a placeholder. The real value must match the App Store Connect record. This may just be the excerpt, but check.
- `Info.plist:13-14`: `MinimumOSVersion` is normally generated by Xcode from the deployment target. Do not rely on hand-set values; check `IPHONEOS_DEPLOYMENT_TARGET`.
- The camera usage string (`:15-16`) is specific and present, which is good. `ITSAppUsesNonExemptEncryption=false` (`:17-18`) is consistent with "first-party frameworks only".
- Missing from this file: `CFBundleExecutable`, `CFBundlePackageType`, `UIApplicationSceneManifest`, and so on. They are probably generated by Xcode (`GENERATE_INFOPLIST_FILE`), so I treat this as an excerpt.

## What is consistent and looks fine
- `NSPrivacyTracking=false`, empty tracking domains and empty collected-data types match "no network, no SDKs, no ads" (`CONTEXT.md:3-5`, `REVIEW_NOTES.txt:7-8`).
- No login is needed, so no demo account is required. `REVIEW_NOTES.txt` gives clear steps.
- First-party frameworks only, so no third-party SDK manifests or signatures to check.

## Could not verify from these files
- That `PrivacyInfo.xcprivacy` is a member of the app target's "Copy Bundle Resources" phase. The team says they added one, but the folder shows no `.pbxproj`. A manifest outside the target would produce a similar email, but the email's specific "Missing API declaration" wording points to finding 1.
- The full Apple email text. It should name the category, which I expect to be `NSPrivacyAccessedAPICategoryFileTimestamp`.
- Source code beyond these two files (other APIs, views, the real PDF rendering).
- App Store Connect items: privacy nutrition labels (should be "Data Not Collected" if the claims hold), privacy policy URL, screenshots, age rating, icons and launch assets, export compliance answers.
- Whether the camera prompt and scanner behave correctly on a device.

## What I would change
1. Add the `NSPrivacyAccessedAPICategoryFileTimestamp` / `C617.1` entry to `PrivacyInfo.xcprivacy`. Keep the UserDefaults / `CA92.1` entry.
2. Confirm the target includes the manifest, and grep the full project for the other required-reason categories (disk space, system boot time, active keyboard, UserDefaults) before the next upload.
3. Replace the stub at `ScannerView.swift:25` with real PDF generation from `scan`, and verify that saved files open.
4. Either use `sortOrder` in `receipts()` or drop it from the notes.
5. Sanitize and uniquify file names. Handle cancel and error in the scanner delegate.
6. Increment the build number and re-upload (build 58) after the fix.
