# Widget Data Consistency

Follow data across process boundaries and distinguish a reload request from an observed widget update.

## Trace the data path

Identify widget kinds/configurations, timeline providers, app intents if used, App Group entitlements on both targets, shared container URLs, persistence formats, and data ownership. Confirm the app and extension actually resolve the same group and schema. The extension cannot rely on the app's in-memory singleton or a continuously running process.

Record timestamps or versions at source update, durable write, reload request, provider read, timeline entry, and displayed result where observable. Avoid logging private widget content. Determine whether stale data originates in the store, provider cache, timeline schedule, or system rendering.

## Inspect consistency

Persist a coherent snapshot before requesting a reload. Review atomic file replacement or database transactions, cross-process access, schema compatibility, and decoding failures. Handle missing/corrupt/unavailable protected data with an explicit fallback. Do not interpret a failed read as permission to overwrite good shared data with an empty value.

Ensure each configuration reads its own selected account/entity. Account logout must clear or invalidate appropriate shared content and request relevant reloads, while acknowledging that already-rendered content may not disappear instantly. Minimize sensitive content and define safe stale states; a reload call is not an immediate privacy guarantee.

Review timeline dates, validity windows, refresh policy, and fallback entries. Predictable changes belong in timelines where practical. Avoid aggressive repeated reloads as a fix: scheduling remains system-controlled. Handle offline and server failure without publishing misleadingly fresh timestamps. Check interactive intent writes use the same consistency rules.

## Verify

Test initial install, no app launch, app write followed by provider read, multiple widget configurations, offline reads, account switch/logout, store migration, and failure during a write. Check small and large families only where their data presentation differs. Preview snapshots do not verify live scheduling; distinguish provider unit tests, simulator rendering, and observed device refresh.

Return the data-flow boundary causing staleness, scoped fix, event/version evidence, and unverified scheduling behavior. Avoid promising exact refresh deadlines that the OS does not guarantee.
