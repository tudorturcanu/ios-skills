# Synthetic on-disk migration probe

## Run and interpret

Requires macOS, Xcode's Swift compiler with Swift 6 support, and SwiftData. The runner has no Python dependencies and performs no network calls. Invoke it through Python from its installed skill directory:

```sh
python3 /absolute/path/to/swiftdata-migration-checker/scripts/run_migration_probe.py
```

Optionally specify `--output /absolute/new/directory`; the directory must not already exist. The default creates a new temporary directory and retains it for inspection. No existing user-store path is accepted. Exit 0 means all checks and the expected negative control succeeded; exit 1 means the probe failed, with details in `results.json` and logs; exit 2 means platform or output-directory setup failed. Compiler failures and failed checks must be investigated, not bypassed by resetting a real app store.

The runner uses `xcrun --sdk macosx swiftc` so Xcode selects the macOS SDK and its SwiftData macros. It compiles in Swift 6 language mode with warnings as errors. V1 contains `title`; V2 renames it to `name` using `originalName`; V3 adds an optional `memo`. Each schema defines explicit inverse parent/children relationships. The source uses main-actor model contexts and synchronous process-local execution.

## What is tested

- V1→V3 directly, V1→V2→V3, and V2→V3.
- Each path with two linked records and an empty store: six cases total.
- Logical UUIDs, Unicode/nondefault names, parent identity, child membership, and record count against an independent expected snapshot.
- Seed semantics before migration; migrated content after opening; persisted content in a fresh process after reopening.
- Exact prior and destination schema-version metadata, including empty stores, using Core Data’s public metadata API.
- Source-fixture file hashes unchanged after copies are migrated.
- A deliberate broken rename: it opens successfully and retains record count and relationships while replacing the names with empty defaults. The negative control must reproduce and detect that specific corruption, rather than counting an arbitrary process failure as success.

The producer exits before the runner copies the whole store directory, including sidecars. Each open/reopen happens in another process. This avoids confusing a still-live context with persisted verification.

## Adapt the method, not the example schema

For an actual app, preserve every shipped version and create fixtures from the relevant released source/toolchain where possible. Replace synthetic fields and expected snapshots with app invariants. Test every supported source release, skipped releases, and relevant edge cases. Stronger assertions may include stable persistent identifiers, ordering, uniqueness conflict policy, deletion behavior, and transformed values; this probe checks logical UUIDs rather than SwiftData's persistent identifier internals.

The schemas here are generated by the current toolchain. They are not historical shipping artifacts and do not prove cross-SDK compatibility. A successful macOS run does not establish every supported iOS version. CloudKit deployment/synchronization, custom migration callbacks, required-field backfills, constraint conflicts, and production data volumes are outside this example.

For migration API behavior and availability, consult [Apple SchemaMigrationPlan](https://developer.apple.com/documentation/swiftdata/schemamigrationplan) and [MigrationStage](https://developer.apple.com/documentation/swiftdata/migrationstage).
